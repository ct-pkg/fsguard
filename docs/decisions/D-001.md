## 裁的是什么

Q-5：负 offset、`len < 0`、`len == 0`、`max_depth < 0` 这些非法参数用什么错误码；推荐案必须与 R-08「非法参数返回 NULL，且原对象状态不变」自洽。

## 两案对比

| 案 | 行为 | 代价 | 与现有条款的关系 |
| --- | --- | --- | --- |
| A（推荐） | 不加第 11 码；`read_chunk` 负 offset / `len<0` → -1 + `FS_ERR_IO`；`len==0` → 0；setter `max_depth<0` → NULL，不置 `last_error`，原对象不变 | 非法参数与 IO 共用 `FS_ERR_IO`；setter 没有诊断码 | 保持 R-02 的 10 码冻结；R-08 原文不变 |
| B | 新增 `FS_ERR_INVALID`；`read_chunk` 非法参数 → -1 + `FS_ERR_INVALID`；setter 仍只返回 NULL | 必须改 R-02 的「恰有 10 个成员」；setter 仍无法在不改 R-08 的前提下报出新码 | 与 R-02 冲突；若要 setter 也报码，还要改 R-08 |

## 裁定

选 **A**。冻结口径：

- `read_chunk(path, offset, buf, len)`：`offset < 0` 或 `len < 0` 返回 -1，`FsGuard` 层 `last_error().code == FS_ERR_IO`；`len == 0` 返回 0。
- `max_depth(n)`：`n < 0` 返回 NULL，原对象配置与 `last_error` 均不改变。
- 不新增 `FS_ERR_INVALID`，R-02 仍为 10 个成员。

## 理由

1. R-08 判据 5 原文是「非法参数（如 `max_depth < 0`）返回 NULL，且原对象状态不变」；若 setter 同时置 `FS_ERR_IO`，就改了 `last_error`，与「状态不变」冲突。A 案只返回 NULL，直接满足。
2. Q-5 原文的「`max_depth<0` 返回 NULL + `FS_ERR_IO`」在现有 API 形态下不可观测：setter 返回的是 `FsGuard *`，失败时拿到 NULL，没有对象可读 `last_error`。A 案把这个不可能的承诺删掉。
3. B 案不能解决 setter 的诊断问题：要报 `FS_ERR_INVALID` 仍得在失败时写原对象的 `last_error`，仍然违反 R-08。它只改善 `read_chunk` 的区分度，却要改 R-02 的 10 码冻结，收益不抵成本。

## 代价

- `read_chunk` 的非法参数与真实 IO 错误共用 `FS_ERR_IO`，调用方无法只靠错误码区分「参数错」与「磁盘错」；需要区分时只能看 `message`。
- setter 非法参数没有错误码，只能通过 NULL 判断。

## 连带改动（引用原文，正文未动）

1. `requirements.md:347`（Q-5 建议）原文：「不新增：负 offset 与 `len<0` 返回 -1 + `FS_ERR_IO`，`len==0` 返回 0，`max_depth<0` 返回 NULL + `FS_ERR_IO`；保持 10 码冻结」  
   拟改为：「不新增：负 offset 与 `len<0` 返回 -1 + `FS_ERR_IO`，`len==0` 返回 0；`max_depth<0` 只返回 NULL，不置 `last_error`，原对象状态不变。」
2. `requirements.md:193`（R-11 判据 1）原文：「每次公开操作开始清错；失败置码（0 表示无错）。」  
   拟明确：「每次读写/遍历/check 公开操作开始清错；配置 setter 的参数校验失败不进入执行路径，不改变 `last_error`。」否则 A 案与 R-11 的宽口径冲突。
3. `requirements.md:78`（R-04 判据 4）：负 offset 的「冻结值」由本 D 冻结为 `FS_ERR_IO`，原文不改。
4. `requirements.md:152`（R-08 判据 5）：原文不改；A 案与其「原对象状态不变」一致。
5. `requirements.md:183`（R-10 判据 5）：`max_depth<0` 返回 NULL、原对象状态不变；原文不改。
6. `requirements.md:47`（R-02 判据 2）：「恰有 10 个成员，名字与数值冻结」；A 案不改。

## 若选另一案会打破什么

选 B 必须改 `requirements.md:47`「恰有 10 个成员」为 11，并同步所有「10 码」断言；如果还要让 setter 报 `FS_ERR_INVALID`，必须把 `requirements.md:152` 的「返回 NULL，且原对象状态不变」改成「返回 NULL，并在原对象置 `FS_ERR_INVALID`」，这直接推翻 R-08 的现状不变承诺。

## 失效条件

- 后续要求「非法参数必须能与 IO 错误区分」且接受改 R-02 的码表；或
- 后续要求 setter 失败必须带诊断码，并同意同时改 R-08 的「原对象状态不变」。
