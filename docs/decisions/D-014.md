## 裁的是什么

D-011 曾裁定：fsguard 不新增 `dep = std`，`ct.pkg` 保持零依赖，std 只在消费者侧按需并存。现在要回答：

1. D-011 是否仍成立？
2. 若不再成立，门禁应偏向「必须有 std 依赖」还是「声明了就必须可解析并记入 lock」？

## 方向核对（大决定前置）

| 核对项 | 结论 |
| --- | --- |
| R-03 判据 1/2（`docs/requirements.md:60-61`） | 要求同文件 import `std::fs::Fs` / `std::str::String` 与本包，并对同一 `char *` 运行时断言 → **std 必须在构建里可用** |
| R-16 判据 1/2（`docs/requirements.md:239-241`） | 约束「不改 std 仓」「不暴露同名方法」，**没有**要求「不依赖 std」 |
| roadmap PH-04（`docs/planning/fsguard-roadmap.md:60-66`） | 把 R-03 的 std 共存列为 PH-04 退出内容 |
| 需求与 roadmap 是否出现「零依赖」约束 | **没有**；「零依赖」只存在于 D-011 的结论与其派生文档 |

因此「fsguard 依赖 std」不与大方向冲突，D-011 可以被取代；取代理由是对其前提的证伪，不是让门禁变绿。

## 两席意见

| 席 | 主张 | 依据 |
| --- | --- | --- |
| proposer（PKG） | 取代 D-011，门禁取「声明即须可解析并记入 lock」 | std 0.3.2 已是 MIT；`ct get` 落共享包根、`ct build` 读 lock 自动补 `-I`，不需要 `vendor`；R-03 的验收要求两个包在同一构建单元并存 |
| opposition（ZERO-DEP） | 维持零依赖，避免把 std 的版本节奏绑进来 | 依赖会多一个包根；std 破坏性升级会传导 |
| evidence（ARCH） | 两席都可实现，但只有 proposer 与实际验收路径一致 | 临时 `-I` 让测试环境偏离消费者路径（`fsguard-std-overlap.md §7` 已有前车之鉴）；D-011 的「自足」理由已被共享包根 + lock 取代 |

## 裁定

选 **B**：

- D-011 标 `superseded`，由本条取代；D-011 的「不拆包、单命名空间」结论**继续有效**，不随之失效。
- `ct.pkg` 保留 `dep = std@0.3.2`；`ct.lock` 提交进版本库；`vendor/` 不进版本库。
- 门禁口径：**声明了就必须可解析并记入 lock**；不强制「必须有 std 依赖」。
- 保留两条反向守卫：死声明（`dep` 有、lock 无或版本不一致）判红；隐式依赖（import 了但没声明）由 `ct verify` 与 R-03 用例构建兜住。

## 判据

1. `grep -x 'dep = std@0.3.2' ct.pkg` 命中；`ct.lock` 含 `std/std 0.3.2` 行，版本与 `ct.pkg` 一致（可核对）。
2. `ct verify` rc=0；`ct install` rc=0（`.m.ct` 的 install 缺陷见 FSG-02，不作为本条判据）。
3. `bash tools/check.sh g0-decisions` 在新口径下 rc=0；删掉 `ct.lock` 的 `std/std` 行后必须 rc≠0（g6 负例）。
4. R-03 判据 1/2/3 的用例在只有 `dep` + `ct.lock`、`vendor/` 不存在的条件下构建并运行通过（`bash tools/check.sh g3-ph04 r03`）。
5. `src/fsguard/` 仍是唯一命名空间目录（D-011 的拆包结论未变）。
6. D-011 的 `status` 为 `superseded` 且正文指向本条。

## 理由

1. **前提证伪，不是口味变化**：D-011 的许可理由建立在 std 为 GPL 之上；std 0.3.2 的 `ct.pkg` 写 `licence = MIT`，本地仓 `64d51c1` 起 LICENSE 同为 MIT。许可义务这条不成立。
2. **「不自足」的理由也被工具链解决**：v0.62.0 的 `ct get` 落共享包根、`ct build` 读 lock 补 `-I`；实测 cc 行只引用 `~/.ct/pkg/std/std/0.3.2/**`，没有任何 `vendor/`。
3. **B 比 C 更像一致性检查**：C（必须有依赖）把「实现是否需要 std」写死成政策；B 只保证「写了就是真的、真用就必须写」。R-03 的用例本身就是「必须存在且可用」的守卫。
4. **与 R-03 的验收路径一致**：门禁、测试、消费者三处用同一套 `dep` + lock 解析，避免「测试靠临时 `-I`、消费者靠包管理器」的双轨。

## 代价

- 消费者多一个包根；`-I` 由 lock 自动补，手工命令只在需要锁定构建时加 `--locked`。
- std 的破坏性升级会表现为显式提交（`dep` + `ct.lock` 同步），需要一次评审。
- 需要维护 `ct.lock` 的版本一致性；门禁多一条「死声明」检查。

## 若选另一案会打破什么

- 选 A（维持 D-011）：R-03 判据 1/2 只能用临时 `-I` 过，测试环境与消费者路径分叉；而 D-011 自己的两条理由都已不成立，等于用过期结论压新事实。
- 选 C（必须有 `dep`）：`ct.pkg` 被绑死为「一定依赖 std」，与「依赖是实现选择」冲突；将来 std 若拆分或改名，需要先改政策才能改实现。

## 残留风险

| # | 风险 | 处置 |
| --- | --- | --- |
| K-1 | std 0.4.x 破坏性升级 | `dep = std@0.3.2` 钉版本；升级必须同时改 `ct.pkg` 与 `ct.lock` 并过 g0 |
| K-2 | `ct.lock` 与 `dep` 漂移 | g0 校验版本一致；g6 负例覆盖 |
| K-3 | `ct install` 在 `.m.ct` 消费者上仍红 | 登记 FSG-02；验收走 `ct build` + 运行 |
| K-4 | 误读为「必须有依赖」 | 本条判据与 g0 实现都只校验「声明即真」，不校验「必须声明」 |

## 失效条件

- std 的许可再次变更（例如回到 copyleft）且与 MIT 分发不兼容时，重开本条评估依赖方向。
- `ct` 若支持在同一 `ct.pkg` 里声明可选依赖（feature/optional），重评「声明即须可解析」的粒度。
- 出现第二个包需要与 fsguard 共享路径词法时，按 D-011 原失效条件重评拆包（拆包结论未随本条失效）。
