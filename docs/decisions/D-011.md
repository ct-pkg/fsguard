## 裁的是什么

> **取代说明（2026-11-16，D-014）**：本节之后凡涉及「不新增 `dep = std` / `ct.pkg` 零依赖 / 硬依赖使构建不自足」的结论，**已由 D-014 取代**。取代依据：std 0.3.2 的 `ct.pkg` 为 `licence = MIT`（D-011 的 GPL 许可前提失效）；`ct v0.62.0` 的 `ct get` 落共享包根、`ct build` 读 `ct.lock` 自动补包含根，不再需要 `vendor/`（「不自足」前提失效）；R-03 判据 1/2 本来就要求 std 与本包在同一构建单元并存。
> 本裁定中「不拆 path 包、`src/` 保持单命名空间」的部分**继续有效**。

以 `ct-pkg/std` 0.2.0 的实际能力为前提，回答两个问题：

1. fsguard 哪些实现在重复 std，该删或改成依赖？
2. 是否应把纯路径一半（`normalize_to`、`is_under`、段边界）拆成独立 path 包，fsguard 只留 fs 操作与 errno 映射？

## 两席意见

| 席 | 主张 | 依据 |
| --- | --- | --- |
| proposer（STD-FACT） | 不依赖、不拆包 | 12 个公开符号与 std 零重复；最接近的 `read_file`/`write_file` 是「同形不可替代」（std 目录读返回 0、失败统一 `-1`、按 `strlen` 写）；`normalize_to`/`is_under`/`read_chunk`/`walk` 在 std 没有对应物；两包方法名交集为空，同单元 import 实测可编译可运行 |
| opposition（SPLIT） | 拆出 path 包更「单一职责」 | 规范化与段边界确实是纯词法，与 errno/IO 无关；拆开后 fsguard 更薄 |
| evidence（ARCH） | 拆包成本大于收益，且无消费者 | 当前下游 `ct-http`/`ct-json`/`rill-dsl` 没有一个 import fsguard（`rill-dsl` 自带 vendored `json`）；拆包后消费者要两个包根、两个 `-I`，而 path 半区没有独立消费者；`ct install` 只按包打印 `-I vendor/<包名>`，包数直接变成根数；std 的 GPL-3.0-or-later WITH GCC-exception-3.1 与 fsguard MIT 不同，无条件的 `dep = std` 会把许可义务带进 MIT 包 |

## 裁定

选 **A**。

- fsguard 不新增 `dep = std`，`ct.pkg` 保持零依赖；std 只在消费者侧按需并存。
- 不拆 path 包。`normalize_to` / `is_under` / 段边界 / deny 方言继续留在 fsguard；它们与 `check`、错误码、遍历同属「策略层」，拆开会让 `check` 跨包调用纯词法，反而增加根数与版本耦合。
- 分工：std 管 `exists` / 整文件便捷读写 / 单层 `list` / 字符串与 IO；fsguard 管策略判定、错误码分类、二进制读写、offset 读、递归遍历与剪枝。
- std 的缺口（目录读返回 0、按 `strlen` 写、无 errno、无 offset/递归）**只出建议**，不改 std 仓库；建议见对照文档 §6 的 S-1…S-4。
- 拆包问题保留复核入口：出现第二个 path 消费者时重开（见失效条件）。

## 判据

1. `docs/reviews/fsguard-std-overlap.md` 含 §3 的 12 行符号对照与 §5 的 6 条语义冲突（可核对：`grep` 小节标题与行数）。
2. 共存探针在同一单元 import `fsguard::FsGuardOps` 与 `std::fs::Fs`，`ct build -I src -I vendor/std` 后 rc=0（记录在对照文档 §4）。
3. `ct.pkg` 不含 `dep = std`（可核对：`grep -v '^#' ct.pkg | grep -q '^dep = std'` 必须为假）。**已由 D-014 取代**：现行口径是「声明了就必须可解析并记入 `ct.lock`」。
4. 源码仍是单包单命名空间：`src/fsguard/` 下不再出现第二个顶层命名空间目录（可核对：`find src -maxdepth 2 -type d`）。
5. 对照文档 §6 记录 S-1…S-4 四条建议，且明确「未改 std 仓库」。

## 理由

1. **零重复是事实，不是感觉**：fsguard 的 12 个公开符号逐条对照后没有一条能直接换成 std 调用；`read_file`/`write_file` 外形相似但错误模型与二进制语义不同，替换会丢掉 R-14 的分类能力。
2. **拆包的收益是假设，成本是确定的**：多一个包 = 多一个 `-I` 根、多一份 `ct.lock` 行、多一次版本协调；而当前没有任何下游包 import fsguard，path 半区也没有第二个消费者。
3. **namespace 与双根实测可行**：两个 `-I` 根并存、两包方法名不冲突，已经用同一编译单元验证（对照文档 §4）；不需要为「避免冲突」而拆包。
4. **许可方向**：std 是 GPL-3.0-or-later WITH GCC-exception-3.1，fsguard 是 MIT；把 std 变成 fsguard 的硬依赖会改变 fsguard 的分发义务，收益却为零。
5. **真正的包形态问题另有其人**：`ct install` 只打印 `-I vendor/<包名>`，而 fsguard 的单元在 `src/fsguard/`，消费者实测报 `cannot resolve import 'fsguard/FsGuard'`。这是 PH-04 的包形态任务，不是拆包能解决的。

## 复判：按「直接改实现、删掉重复部分」逐函数核对

| 候选 | 结论 | 卡点（实测/代码） |
| --- | --- | --- |
| `FsGuard::read_file` → `std::fs.readFile` | 不可替换 | std 无 errno；读目录返回 0；换掉会丢 `FS_ERR_NOT_FOUND`/`PERMISSION`/`IS_DIR` 与 `BUFFER_TOO_SMALL` 的区分（R-14） |
| `FsGuard::write_file` → `std::fs.writeFile` | 不可替换 | std 按 `strlen` 写、成功返回 0；换掉会丢二进制与返回 `len`（R-12 / D-006） |
| `FsGuard::read_chunk` / `char *::read_chunk` → `std::io::File` | 不可替换 | `IoFile` 无 `seek`/offset；只能顺序 `read` |
| `walk` → `std::fs.list` | 不可替换 | `list` 单层、`\n` 拼接、无类型；且 walker 在 C shim，无法调用 CT 映射方法 |
| `fsguard_errno_to_code` → std | 不可替换 | std 不暴露 errno |

结论：可删实现 **0 行**；代码保持现状，差异写进 README 与 `docs/acceptance/fsguard-commands.md`。
硬依赖 std 还要求每个消费者与门禁都持有 `vendor/std`，而 `vendor/std` 不进版本库（主控约束），
会把构建变成非自足，因此「零依赖」同时是工程约束。

## 失效条件

- std 增加 errno 出口、offset 读或递归遍历，且语义与 fsguard 一致时，重评「同形不可替代」的结论。
- 出现第二个包需要路径规范化/段边界（例如 ct-http 要做静态文件路由），重评拆包与依赖方向。
- `ct` 的包工具支持一个包内多个命名空间根，或支持消费端的 `-I` 自动推导，重评 `src/` 布局的处置成本。

## 影响

- `ct.pkg` 保持无依赖；探针安装的 `vendor/std` 与 `ct.lock` 不提交（本地对照用，命令见对照文档 §1）。
- `g0-decisions` 增加 D-011 的 13 字段与「无 std 硬依赖」守卫。
- R-01/R-03 的包形态缺口（`src/` 与 `ct install` 不兼容）登记到 PH-04，不在本裁定内动源码布局。
