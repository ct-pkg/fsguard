## 裁的是什么

PH-04 的后半有四项依赖外部条件，其中 R-01 判据 2/3（消费者只 import 本包）与 R-02 限定名（`FsErrCode::FS_ERR_*`）是否继续留在 PH-04 的退出判据里。留着，E-8 使 PH-04 无限期不能收口；移走，必须证明不是「为了过门禁放宽判据」。

## 裁定

选 **C**，并分两种理由：

- **R-01 判据 2/3 按归属移出。** 上游阻塞已消失：PKG-2 已解决（v0.55.0 `ns-root`、v0.58.0 `ct build` 读 lock）；本机 ct v0.58.0 实测 `ct install` 打印 `-I …/src`、`ct build` 不再报 `cannot resolve import`。剩余工作是本仓提交 `publisher`/`ns-root` 与建消费者夹具，属打包 1.1，不是「等上游」。
- **R-02 限定名按上游依赖移出。** LANG-15 仍 open，已排 PH-57 → v0.59.0；本机 v0.58.0 实测仍报 `qualified type names are not supported`。触发条件写死为版本号，不按日历等。

两条例目的判据原文、验收命令与需求条目全部保留，只改归属；PH-04 卡保留一席之地记录去向（「裁定记录」节）。

## 判据

1. `docs/phases/PH-04/card.md` 的 E-7 只枚举 R-03、R-17 两项挂起；E-8 写「R-03/R-17 仍挂起时不得收口」（可核对）。
2. `docs/planning/fsguard-roadmap.md` §3 有 R-01 判据 2/3 与 R-02 限定名两条去向，含触发条件与验收命令（可核对）。
3. `docs/planning/fsguard-packaging.md` 1.1/1.5 记「上游已具备」与本仓剩余项（可核对）。
4. `docs/requirements.md` 的 R-01 判据 2/3、R-02 判据 2 原文未改（`grep` 仍含两种写法）。
5. `bash tools/check.sh g3-ph04 all` rc=0（卡内挂起标记词保留）；`bash tools/check.sh all` rc=0；`ct pkg check .` rc=0。
6. 移出条目在 PH-05 承接：R-01 2/3 为首任务，R-02 触发 `ct >= v0.59.0` 后复跑限定名用例。

## 理由

- A 对 R-01 的前提已被上游推翻；继续等是空等，且没有任何证据能证明「还在缺」。
- B 会改判据：R-02 判据 2 明确要求裸名与限定名**分别** assert，只留裸名不能证明原主张；R-01 退到源码根构建则绕开「消费者只 import」这一条。
- C 不删判据、不降宽度，只把「谁负责、何时触发」写清；PH-04 的收口强度（前半全绿）不变，只是不再被不相干的上游排期绑架。

## 代价

- PH-04 的实际交付范围比 roadmap 原计划窄：R-01 只交判据 1/4。
- 需要维护三处去向记录（D-013、roadmap §3、卡面裁定记录），漏一处就会变成「静默删除」。
- 移出两条不改变 PH-04 仍被 R-03（共享库）与 R-17（Linux）挡住的事实。

## 若选另一案会打破什么

- 选 A：E-8 与 PH-04 卡长期停在 `in-progress`；R-01 明明已可做却被登记为「等上游」，后续读者会按错误前提行动。
- 选 B：R-02 的门禁从「证明限定名可用」退化为「证明常量可用」，证据与主张脱节；这正是 6.7 与 G1 要防的「为过门禁改判据」。
